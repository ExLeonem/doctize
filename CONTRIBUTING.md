# Contributing to Doctize

Thank you for helping. This document explains how to build the project, how it is tested, and what a good change looks like.

## Building

You need network access for the first build. Gradle 9 needs a JDK 17 or newer to run; it downloads the JDK 25 toolchain
that the code is compiled with. Node.js 18 or newer is used for the tests of the search engine; without it these
tests are skipped.

```console
$ export JAVA_HOME=/path/to/jdk-17-or-newer
$ ./gradlew build                          # everything below
$ ./gradlew :doctize-docs:generateDocs     # the documentation → doctize-docs/build/docs
```

## How the project is tested

Tests exist on four levels, and a change should be tested on the lowest level that can show it.

| Level | Where | What it covers | Run it alone |
|-------|-------|----------------|--------------|
| **Unit** | `src/test` of each module | One class or a small group of classes, without I/O beyond temporary files | `./gradlew test` |
| **Integration** | `doctize-tests/src/integrationTest` | Modules working together, in one process: real `javac` + the annotation processor + the generator, custom themes, several modules in one site, the search engine in Node.js | `./gradlew :doctize-tests:integrationTest` |
| **System** | `doctize-tests/src/systemTest` | The product as a user gets it: the installed CLI as a subprocess, and the artifacts that would be published, resolved the way a downstream build resolves them | `./gradlew :doctize-tests:systemTest` |
| **Documentation** | `doctize-docs`, `doctize-example` | The docs of Doctize, generated by Doctize, must build without warnings and name the current version | `./gradlew :doctize-docs:check` |

Guidelines:

- A bug fix starts with a test that fails. Put it where the bug lives: a parsing bug gets a unit test, not a system test.
- Unit tests should describe behaviour in their names (`aNestedTypeWithItsOwnPageIsReachedThroughThatPage`), not methods.
- The sample libraries of the integration tests are in `doctize-tests/src/integrationTest/resources`. Extend them when a
  new Java construct or documentation feature needs coverage.
- `SiteCrawler` (in `doctize-tests/src/support`) checks that a generated site has no broken link, asset or anchor.
  Use it when a change touches links, URLs or output layout.

Coverage reports are written to `<module>/build/reports/jacoco/test/html` by `./gradlew test`.

## Code style

- The compiler runs with `-Xlint:all -Werror`; warnings fail the build.
- Follow the surrounding code: small classes with one responsibility, records for data, no static mutable state,
  comments that explain *why*. See `.editorconfig` for formatting.
- The public API is documented with Javadoc, and the documented types carry `@Doc`, because this project documents itself.
  If you add a public type, annotate it and give it a `group` and `order` so it appears sensibly in the reference.
- Do not add a dependency lightly. `doctize-annotations` must stay dependency-free, and `doctize-core`'s dependencies
  are part of what every user downloads.

## Documentation

Guides are Markdown files in `doctize-docs/docs`. If you change behaviour or options, update the guide that describes
them. `./gradlew :doctize-docs:check` fails on unresolved `{@link}`s and on a mismatch between the documented and the
actual version.

## Pull requests

1. Fork the repository and create a branch.
2. Make the change with its tests, and run `./gradlew build`.
3. Add a line to `CHANGELOG.md` under "Unreleased".
4. Open a pull request and fill in the checklist.
