# Doctize

Doctize turns the **Javadoc of your annotated Java code** and a folder of **Markdown guides** into a
modern, searchable documentation site. You decide the structure: "Quick start", "Setup", "Recipes" or
anything else is a section, and adding one takes a folder or one line of YAML.

* **Write docs where they belong.** Annotate a type with `@Doc`; its Javadoc, and the Javadoc of its
  members, becomes an API reference page. Classic `/** */` comments and Markdown `///` comments
  ([JEP 467](https://openjdk.org/jeps/467)) both work.
* **Structure is yours.** Sections, their order and their teasers come from `doctize.yml`, from folders,
  from front matter or from code.
* **Search that finds things.** Full-text, typo tolerant, camelCase aware ("builder" finds
  `CacheBuilder`), deep links to headings and API members, `Ctrl/⌘ K`. It runs offline and also works
  when the site is opened from the file system.
* **A theme you can change in ten minutes.** Light and dark mode, syntax highlighting rendered at build
  time (no JavaScript needed to read), code tabs, admonitions, responsive layout. Override one template,
  one stylesheet or everything.
* **Static output.** Plain HTML, CSS and a little JavaScript; host it anywhere.

**The documentation of Doctize was generated by Doctize itself**: the API reference comes from the Javadoc in
this repository, the guides from [`doctize-docs/docs`](doctize-docs/docs). Build it with

```console
$ ./gradlew :doctize-docs:generateDocs      # → doctize-docs/build/docs/index.html
```

The [`doctize-example`](doctize-example) module documents a small fictional library, as a demo and a living
integration test (`./gradlew :doctize-example:generateDocs`).

## Quick start

**1. Add the annotations and the processor** to the library you want to document:

```kotlin
dependencies {
    compileOnly("dev.doctize:doctize-annotations:0.1.0")
    annotationProcessor("dev.doctize:doctize-processor:0.1.0")
}
```

**2. Annotate and document your types:**

```java
/// A cache maps keys to values and evicts entries once it is full.
///
/// > [!TIP]
/// > Prefer {@link #getOrLoad(Object, Function)} over `get` followed by `put`.
///
/// @param <K> the type of keys
/// @since 1.0
@Doc(order = 1)
public interface Cache<K, V> { /* ... */ }
```

At compile time the processor writes `META-INF/doctize/model.json` into your class output.

**3. Scaffold the site and generate it:**

```console
$ doctize init                       # creates doctize.yml and starter guides in docs/
$ doctize generate --model build/classes/java/main --output build/docs --serve
```

The `doctize` command is built by `./gradlew :doctize-cli:installDist` (`doctize-cli/build/install/doctize/bin`)
and needs Java 25 to run.
You can also run it from Gradle, as [the example does](doctize-example/build.gradle.kts), or call the API:

```java
Doctize.builder()
        .configFile(Path.of("doctize.yml"))
        .model(Path.of("build/classes/java/main"))   // repeat for more modules
        .output(Path.of("build/docs"))
        .build()
        .generate();
```

## What ends up on the site

| Source | Becomes |
|--------|---------|
| A type annotated with `@Doc` | An API page: signature, description, and constructors, fields, methods, nested types with parameters, return values, exceptions and tags |
| `package-info.java` or a type annotated with `@DocPage` | A prose page: the comment *is* the page (Markdown) |
| A `.md` file in the guides directory | A guide page |
| `index.md` in the guides directory | The introduction on the home page |
| Any other file in the guides directory (images ...) | A published asset |

> The sections below are a summary. The [generated documentation](doctize-docs/docs/index.md) has the full guides:
> writing documentation, structuring the site, theming, the template reference, extending Doctize.

### Annotations

| Annotation | Attributes |
|------------|------------|
| `@Doc` (types) | `section`, `title`, `order`, `group`, `keywords`, `members` |
| `@DocPage` (types, packages) | `section`, `title`, `order`, `group`, `keywords` |
| `@DocIgnore` (members) | hides a member from the reference |

Public and protected members of a `@Doc` type are documented (all members of an interface). Members the
compiler generates (`values()`, record accessors ...) are only listed when you wrote a comment for them.

### Javadoc

Comments are Markdown; classic HTML Javadoc keeps working because Markdown allows inline HTML.

* Block tags: `@param`, `@return`, `@throws`/`@exception`, `@deprecated`, `@see`, and any other tag
  (`@since`, `@apiNote`, `@author`, `@example` or your own) which is shown as a labelled block.
* Inline tags: `{@code}`, `{@literal}`, `{@link}`, `{@linkplain}`, `{@summary}`,
  `{@index}`, `{@snippet}` (inline content only). `{@link}` targets are resolved across all documented
  types: `Cache`, `com.acme.Cache`, `Cache#get(Object)`, `#size`.
* JEP 467 reference links: `[Cache]`, `[Cache#get(Object)]`, `[the cache][Cache]`. Brackets that name
  no documented element are left as plain Markdown.
* `<pre>{@code ...}</pre>` blocks become highlighted code blocks with a copy button.
* Markdown extensions: tables, task lists, strikethrough, autolinks, and GitHub alerts
  (`> [!NOTE]`, `TIP`, `IMPORTANT`, `WARNING`, `CAUTION`).
* Fenced code blocks accept `title="..."`; consecutive blocks with `tab="..."` become one tab group and
  the reader's choice (Gradle, Maven ...) is remembered across the site:

  ````markdown
  ```groovy tab="Gradle"
  implementation 'dev.acme:cache:1.0'
  ```

  ```xml tab="Maven"
  <dependency>...</dependency>
  ```
  ````

## Structuring the documentation

The structure is a list of **sections**, each a group of pages in the navigation. There are four ways to
shape it; they combine freely.

**1. `doctize.yml`.** The order of `sections` is the order in the navigation. Write a section as a plain
title, or as a mapping with `id`, `title` and `description` (shown on the home page).

```yaml
project:
  name: Acme Cache
  tagline: A small, fast, bounded in-memory cache for Java.
  version: 1.2.0
  repository: https://github.com/acme/acme-cache
  footer: © 2026 Acme Corp.

guides: docs                # Markdown directory, relative to this file
defaultSection: Guides      # for guides that are neither in a sub-directory nor name a section

sections:
  - id: quick-start
    title: Quick start
    description: Add the dependency and cache your first value.
  - Setup                   # shorthand
  - Guides
  - id: api
    title: API Reference

api:
  section: API Reference    # where @Doc types without a section go
  includeUndocumented: true # list members that have no doc comment
```

**2. Folders.** A sub-directory of the guides directory is a section: `docs/setup/install.md` lives in
"Setup". A numeric prefix orders files and folders and is dropped from names
(`01-quick-start/02-install.md`). A folder that is not declared in `doctize.yml` still creates a
section, appended after the declared ones.

**3. Front matter.** Every option can be set per file:

```markdown
---
title: Installation        # default: first "# heading", else the file name
section: setup             # id or title; default: the folder
order: 10                  # default: the numeric prefix, else 100
group: How-to              # label that groups pages in the navigation
slug: install              # file name of the page
description: One line for cards and search results.
keywords: [gradle, maven]  # extra search terms
---
```

**4. Java code.** `@Doc(section = "Caching")` and `@DocPage(section = "Guides", order = 10)` place
generated pages; `Doctize.builder().section("Quick start").section("Setup")` declares sections in code
(and replaces the list from the config file). To contribute pages from any other source, e.g. a
changelog, implement `PageSource` and register it with `builder.pageSource(...)`.

Relative links between Markdown guides just work: `[Setup](../setup/install.md)` points to the generated
page, `![](../images/x.svg)` to the copied asset, and `[eviction](../guides/eviction.html)` to a
generated page by its URL.

## Theming

A theme is a directory that is **layered over the built-in theme**, so it only contains what it changes.

```yaml
theme:
  path: my-theme            # optional custom theme directory
  accent: "#0d9488"         # colour of links and highlights
  extraCss: [brand.css]     # added after the theme's stylesheet
  extraJs: [brand.js]
  options: { hero: dark }   # free-form values for your templates: {{theme.options.hero}}
```

```
my-theme/
  templates/
    layout.mustache               the page frame
    home.mustache  guide.mustache  api-type.mustache
    partials/footer.mustache      header, sidebar, toc, pager, search, member, tags, ...
  assets/
    css/theme.css                 replaces the built-in stylesheet
    img/logo.svg                  a new asset, published as assets/img/logo.svg
```

* **Restyle without forking:** every colour, width and font is a CSS custom property
  (`--accent`, `--content-width`, `--font-sans` ...). Override them in an `extraCss` file.
* **Templates are [Mustache](https://mustache.github.io/)**: logic-less, so everything they show is
  prepared in Java (`dev.doctize.render.Views`). `{{value}}` is HTML-escaped, `{{{valueHtml}}}` is not,
  `{{> partials/name}}` includes a partial. URLs in views are relative to the site root, so prefix them
  with `{{basePath}}`; that keeps the site working under any sub-path and from `file://`.
* Every page gets `layout.mustache` with `project`, `theme`, `navigation`, `toc`, `previous`, `next`,
  `section`, `title`, `contentHtml` and `basePath`. The body comes from `guide`, `api-type` or `home`.

## Publishing to GitHub Pages

```console
$ doctize init --github-pages                 # adds hosting settings and .github/workflows/docs.yml
$ doctize generate --github-pages --base-url https://acme.github.io/cache/
```

`--github-pages` writes `.nojekyll` (and `CNAME` for `--cname docs.acme.dev`). Once the address of the site is known
(from `--base-url`, a custom domain, or `project.repository`) Doctize also writes a `404.html` that works at any depth,
`sitemap.xml`, `robots.txt` and canonical links. The workflow in `.github/workflows/docs.yml` publishes this repository's
own documentation; see the guide *Publishing to GitHub Pages* in the generated docs.

## Command line

```
doctize generate [-c doctize.yml] [-m <classes-dir|model.json|jar>]... [-g docs] [-t theme]
                 [-o build/docs] [--github-pages] [--base-url <url>] [--cname <domain>]
                 [--serve [--port 8080]]
doctize init [dir] [--name "My Library"] [--github-pages]
```

`generate` uses `./doctize.yml` when it exists; options override the file. The output directory is
cleaned on every run, but only if Doctize created it (it contains a `.doctize-site` marker), so a wrong
`--output` cannot delete your files.

## Project layout

| Module | Purpose |
|--------|---------|
| `doctize-annotations` | `@Doc`, `@DocPage`, `@DocIgnore`: the only dependency of documented code (`compileOnly`) |
| `doctize-processor` | Annotation processor: extracts elements and raw doc comments into `model.json` |
| `doctize-core` | Generator library: Javadoc and Markdown handling, site structure, search index, theme engine |
| `doctize-cli` | The `doctize` command |
| `doctize-docs` | The documentation of Doctize, generated by Doctize. It compiles the sources of the annotations and of `doctize-core` a second time with the processor enabled, because the processor cannot run inside the modules it is built from |
| `doctize-example` | A sample library and its documentation, used as a living integration test |

The pipeline: processor → `model.json` → **page sources** (API elements, guide directory, yours) →
**site assembler** (sections, order, URLs) → **page renderer** (inline tags → Markdown → HTML, views)
→ **theme templates** → HTML plus `search-index.js`.

## Building

Requires network access on the first build. Java 25 is provisioned automatically by Gradle's toolchain
support, but running Gradle 9 itself needs a JDK 17 or newer as `JAVA_HOME`.

```console
$ ./gradlew build                          # compile, test (Java and, if Node.js is present, JavaScript)
$ ./gradlew :doctize-example:generateDocs  # the example site → doctize-example/build/docs
```

The annotation processor runs because it is on the `annotationProcessor` path. Since JDK 23 javac only
runs processors that are named explicitly, which Gradle does for you; with other build tools pass
`-processorpath` or `-processor dev.doctize.processor.DocProcessor`.

## Known limitations

* Nested types are listed on their owner's page with signature and description, but their own members
  are not. Annotate a nested type with `@Doc` to give it a page of its own with all its members.
* Alerts (`> [!NOTE]`) are only recognised at the top level, not inside list items.
* `{@inheritDoc}` is dropped, not resolved from the supertype, and `{@value}` shows the reference, not the constant's value.
* Syntax highlighting knows Java, Kotlin, Groovy/Gradle, JavaScript/TypeScript, JSON, YAML/properties/TOML,
  shell and XML/HTML; other languages are shown unhighlighted.
* Search indexes the text at build time and builds its index in the browser, which is instant for
  hundreds of pages; for many thousands a pre-built index would be the next step.
