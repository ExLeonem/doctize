# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Doctize turns the Javadoc of `@Doc`-annotated Java code plus a folder of Markdown guides into a static, searchable documentation site. It documents itself: `doctize-docs` is generated by Doctize from its own sources. See `README.md` for the user-facing feature set.

## Commands

Gradle 9 needs a JDK 17+ as `JAVA_HOME`; it provisions the Java 25 toolchain the code compiles with. Node.js 18+ is used by the search-engine tests (skipped if absent).

```console
./gradlew build                                   # everything: unit + integration + system tests + strict docs build + version check
./gradlew test                                    # unit tests only (src/test in each module)
./gradlew :doctize-tests:integrationTest          # real javac + processor + generator, in-process
./gradlew :doctize-tests:systemTest               # installed CLI as subprocess + staged artifacts consumed like a downstream build
./gradlew :doctize-docs:check                     # Doctize's own docs: fails on unresolved {@link}s and version mismatch
./gradlew :doctize-docs:generateDocs              # → doctize-docs/build/docs
./gradlew :doctize-example:generateDocs           # → doctize-example/build/docs
./gradlew :doctize-cli:installDist                # → doctize-cli/build/install/doctize/bin/doctize
```

Single test: `./gradlew :doctize-core:test --tests 'dev.doctize.SomeTest.someMethod'` (same `--tests` filter works on `:doctize-tests:integrationTest` and `:systemTest`).

Extra CLI args for `generateDocs`: `-PdoctizeArgs="--github-pages --base-url https://..."`.

## Build conventions

- Shared build logic is in `buildSrc` convention plugins: `doctize.java-conventions` (Java 25, JUnit 5, JaCoCo, reproducible archives), `doctize.publishing-conventions`, and `doctize.generate-docs` (adds the `generateDocs` task that runs `doctize-cli` on a module's classes + `doctize.yml` + `docs/`). Dependency versions are in `gradle/libs.versions.toml`.
- Compiler runs with `-Xlint:all -Werror`: **any warning fails the build**.
- The project version lives only in `gradle.properties`. `doctize-docs:verifyDocsVersion` fails if `doctize-docs/doctize.yml` or any `dev.doctize:doctize-*:<version>` snippet in `doctize-docs/docs` names a different version. Release steps are in `RELEASING.md`; add changes under "Unreleased" in `CHANGELOG.md`.
- `doctize-annotations` must stay dependency-free. Public types in the documented modules carry `@Doc` (with `group` and `order`) because the project documents itself.
- Published modules (`doctize-licensing` is not one of them): `doctize-annotations`, `doctize-processor`, `doctize-core`, `doctize-cli`, `doctize-gradle-plugin`. The root `build.gradle.kts` stages them into `build/staging-deploy` and builds the Maven Central bundle (`stageArtifacts`, `centralBundle`).

## Architecture

Pipeline (details in `doctize-docs/docs/guides/07-how-it-works.md`):

**annotation processor → `model.json` → page sources → site assembler → page renderer → theme templates → static HTML + `search-index.js`**

- `doctize-processor` (`DocProcessor`) runs in `javac` and writes `META-INF/doctize/model.json` into the class output. It stores the **raw** doc comment; Javadoc/Markdown parsing is deliberately deferred to the generator so improving it never requires recompiling user code. The JSON schema is `dev.doctize.model.SourceModel` (versioned via `formatVersion`).
- `doctize-core` is the generator library; entry point is `dev.doctize.Doctize` (builder → `generate()`). Packages map onto pipeline stages:
  - `model` – reads `model.json`; `config` – `doctize.yml`
  - `site` – `PageSource`s (`ApiPageSource`, `GuideDirectory`) produce `Page`s that say *what* they want (section/order/title) but not where they land; `SiteAssembler` is the **only** place that decides structure/URLs (sections, ordering, dropping empties)
  - `javadoc` + `markdown` – inline tags → Markdown → HTML, heading ids, build-time syntax highlighting, link rewriting
  - `render` – `PageRenderer`, `Views` (view objects for templates), `TypeIndex` (cross-page/module `{@link}` resolution)
  - `theme` – Mustache templates layered over the built-in theme (`src/main/resources/dev/doctize/theme/default`); templates are logic-less, so all display data is prepared in Java
  - `search` – builds `search-index.js`; the search engine itself is JS in the theme assets (`search-engine.js`, `search-ui.js`) and is tested from Node in the integration tests
  - `output`/`hosting` – `SiteWriter`; output dir is only cleaned if it contains the `.doctize-site` marker; GitHub Pages files (`.nojekyll`, `404.html`, sitemap)
- `doctize-cli` – picocli wrapper (`generate`, `init`) around `Doctize`.
- **Licensing and the architecture map** live in `doctize-core`. `dev.doctize.license`: `LicenseVerifier` checks `<json>.<signature>` (Ed25519) against the public key in `license/vendor-public-key.pem`; `LicenseLocator` finds the license (explicit > `DOCTIZE_LICENSE` > `doctize.license` next to the config > `~/.doctize/license`); `LicenseStatus` says whether a `Feature` may be used and why not. `Doctize.generate()` is the one gate: a licensed feature that is switched on but denied is skipped with a **warning**, never an error. `dev.doctize.architecture`: `ClassScanner` reads class files with the JDK's `java.lang.classfile` into `TypeInfo` (members, generics via `Signatures`, annotations, calls; no ASM). `DiagramScope` decides what a diagram may show (marks beat configuration, ignore beats include, see its Javadoc). One generator per kind, each returning `DiagramResult` (Mermaid source + warnings): `ArchitectureAnalyzer`+`OverviewMermaid` (or the SVG `ArchitectureDiagram`), `ClassDiagrams`, `StateDiagrams`, `EntityDiagrams`, `FlowDiagrams`; `ArchitecturePageSource` (an ordinary `PageSource`) turns them into pages via `DiagramPage`/`ArchitecturePage`. Settings are `config.ArchitectureSettings` + `config.DiagramSettings` (one record per kind, YAML shorthand `true`/mapping); a new option goes there, into the generator, `setup/04-configuration.md` and `guides/08-architecture-diagrams.md`. **The Mermaid source you generate is only checked by real Mermaid in a browser**: after changing a generator, build a site and look at it. `dev.doctize.diagram.MermaidAssets` publishes the bundled `mermaid.min.js` only if a guide has a `mermaid` fence; the theme's `diagrams.js` loads it lazily. The marker annotations (`@DiagramIgnore` etc.) have CLASS retention on purpose (bytecode is analyzed), take `String[] types` and never an enum (an enum attribute makes downstream compiles warn), and are read by name from class files, so core needs no runtime dependency on them.
- `doctize-licensing` (not published, must never be a dependency of a published module: `PublishedArtifactsSystemTest` checks) creates the signing key and issues licenses. The private key is `.license/vendor-private-key.pem` (git-ignored; see `RELEASING.md`); system tests use it when present and skip the licensed path otherwise. Tests of core and in-process integration tests use keys made for the test and `Doctize.Builder#licenseVerifier`.
- `doctize-gradle-plugin` – the `dev.doctize` Gradle plugin (`DoctizePlugin`, `doctize { }` extension, `DoctizeGenerate` task). It does **not** depend on `doctize-core`: the task runs the published `doctize-cli` in a separate process on a Java 25 toolchain (`doctizeTool` configuration), and `CliArguments` is the one place that knows the CLI's command line. The module is compiled with `--release 17` (Gradle's JVM may be older than 25) and must stay so. `java-gradle-plugin` adds its own publications, incl. a marker artifact `dev.doctize.gradle.plugin`; `doctize.publishing-conventions` handles that and signs every publication. Unit tests use `ProjectBuilder`; `GradlePluginSystemTest` runs real builds through TestKit against the staged artifacts.
- Output URLs are relative to the site root (`{{basePath}}` in templates) so the site works from `file://` and under any sub-path — keep this invariant when touching links.

The docs of Doctize include a live architecture map of `dev.doctize` when a license is found (`doctize-docs/doctize.license`, `$DOCTIZE_LICENSE`, `~/.doctize/license`; see the end of `doctize-docs/build.gradle.kts`), configured by the `architecture:` block of `doctize-docs/doctize.yml` (`enabled` stays false there; the build passes `--architecture`). Cycle reporting is off there because the docs build fails on warnings and the packages `config`, `hosting`, `output`, `render`, `search`, `site` really are a cycle; the guide `09-architecture-of-doctize.md` documents that and must be updated if the package structure or its rules change.

`doctize-docs` and `doctize-example` use the internal `doctize.generate-docs` convention (a `JavaExec` on `:doctize-cli`), not the plugin: a plugin cannot be applied in the build that produces it. Keep `doctize-docs/docs/setup/03-gradle.md` in step with the plugin's settings; `verifyDocsVersion` also checks `id("dev.doctize") version "..."` snippets.

### Self-documentation quirk

The processor depends on `doctize-core`/`doctize-annotations`, so it cannot run while compiling them. `doctize-docs` therefore adds those modules' source dirs to its own `sourceSets.main` and recompiles them with the processor enabled (Jackson/commonmark/jmustache as `compileOnly`). New third-party dependencies in `doctize-core` must also be added to `doctize-docs/build.gradle.kts` as `compileOnly`, or the docs module stops compiling. Its `generateDocs` runs with `--fail-on-warnings` and is wired into `check`.

### Test layout

- Unit: `src/test` per module.
- `doctize-tests/src/integrationTest` and `src/systemTest` (which also has TestKit for the Gradle plugin) are custom source sets sharing helpers in `src/support` (`SiteCrawler` verifies a generated site has no broken link/asset/anchor — use it when changing links or output layout; `Javac`, `Processes`). Sample libraries are under `integrationTest/resources` (`sample-shop`, `sample-payments`) and are reused by system tests.
- System tests consume the *staged* artifacts from `build/staging-deploy` (a Maven repo) and the installed CLI, so they depend on `stageArtifacts` and `:doctize-cli:installDist`.
- Put a regression test at the lowest level that can show the bug; unit test names describe behaviour, not methods.
